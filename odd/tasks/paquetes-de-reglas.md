# Paquetes de reglas importables desde git

Objetivo: que varias instancias, o la comunidad, reutilicen un conjunto de reglas de una capa (por ejemplo, de Go o de SQL) importándolo desde un repo git fijado a una etiqueta. Rama: `feat/paquetes-de-reglas`, apilada sobre `docs/uso-en-equipo` (`d9d8777`). Entrega: un commit por unidad; push de la rama con destino explícito; `main` y etiquetas solo con autorización. Runner: Python sin pytest, `python <x>.tests.py`. Espejo en Engram: `odd/paquetes-de-reglas/tasks`.

## Specs

- **S1, el pedido.** «Paquetes de reglas importables desde git, por etiqueta.»
- **S2, el alcance (decidido el 2026-11-16, engram `odd-ws/uso-en-equipo-y-paquetes`).** «Paquetes de reglas importables desde git por etiqueta (mediano): por ejemplo, reglas de Go o de SQL que reutilizan varias instancias o la comunidad.»
- **S3, cómo se trae (decisión del usuario, L2).** El paquete se copia a la instancia y se commitea, con un lock que fija su etiqueta y su commit; no es un submódulo.
- **Diseño (decisiones técnicas del orquestador, sobre S1-S3; ver L3):**
  - **D1, el paquete.** Un repo git con, en su raíz: `odd-ws-paquete.json` (`{"formato": 1, "nombre": "<a-z0-9->", "prefijo": "<[A-Z][A-Z0-9]*>", "odd_ws_api": 1, "descripcion": "…"}`), `verificar.py` (el mismo contrato que `verificar_<capa>.py`), `verificar.tests.py`, `matriz.csv` (las mismas columnas, con IDs `<prefijo>-NN`), `no-negociables.md` y `evidencia.md`; `LICENSE` opcional. Nada más se copia: ni subcarpetas ni enlaces simbólicos.
  - **D2, en la instancia.** Se copia a `.claude/reglas/paquetes/<nombre>/`. El lock es `.claude/reglas/paquetes.json`: `{"version": 1, "paquetes": {"<nombre>": {"capa", "prefijo", "fuente", "etiqueta", "commit" (40 hex), "huella" ("sha256:<hex>" de los archivos copiados)}}}`. Lo copiado no se edita a mano: se cambia en el paquete y se reimporta.
  - **D3, los IDs.** Cada paquete trae su prefijo, que no puede chocar con el `rule_prefix` de ninguna capa ni con otro paquete. Sus filas viven en el `matriz.csv` del paquete, no en el de la instancia, así que `/odd-ws:cerrar` sigue numerando solo las propias.
  - **D4, el motor.** Para una capa, el motor corre su `verificar_<capa>.py` y además el `verificar.py` de cada paquete de esa capa según el lock; un hallazgo de un paquete con un id fuera de su prefijo no vale. El primer toque suma el `no-negociables.md` de cada paquete al bloque de la capa. `reglas.py --test` corre también la suite de cada paquete. `matriz.py` valida la matriz de cada paquete contra sus propios archivos (destinos `chequeo`, `pasiva`, `evidencia` y `descarte`). Un paquete que pide un `odd_ws_api` mayor que el del plugin no se carga, y el doctor lo dice.
  - **D5, importar.** `paquetes.py importar <fuente> --etiqueta <etiqueta> --capa <capa> [--ensayo]`, `actualizar <nombre> --etiqueta <etiqueta> [--ensayo]`, `quitar <nombre>` y `listar`. Comprueba que la etiqueta existe (`git ls-remote --tags`), clona solo esa etiqueta en una carpeta temporal fuera de la instancia, compara el commit, valida el manifiesto, copia la lista blanca y escribe el lock. **Nunca ejecuta código del paquete**: lo que corre en los hooks se revisa antes, en el diff. La red se usa solo en `importar` y `actualizar`.
  - **D6, el doctor y la skill.** El ítem `paquetes` del doctor revisa el lock, que cada carpeta exista, que su huella coincida (una edición local da FALTA), los prefijos y el `odd_ws_api`. La skill `/odd-ws:paquetes` (solo tú) corre el ensayo, muestra el plan, importa con tu sí y te pide revisar el código antes del commit.
- **Fuera de alcance (v1):** textos para el revisor (`reviewer-PR`) o `criterios` desde un paquete, subcarpetas dentro del paquete, dependencias entre paquetes y un índice de paquetes de la comunidad.
- **Riesgo:** ítem 2 (el motor carga y ejecuta código que viene de otro repo, dentro de los hooks) e ítem 5 (los paquetes son dependencias). Lleva verificador independiente.
